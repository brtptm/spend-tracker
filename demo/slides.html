Always
Deterministic engine

Every number, every time. Instant fallback for any failure.

Aggregates onlyA ~700-token summary — never raw transactions.
Schema decodingSmall models can only emit valid JSON.
Number groundingAny ₹ figure not in the input is rejected.
Echo rejectionPrompt instructions never reach the user.
Never stuckEvery tier falls back to the next, instantly.
This is the part we're proudest of. Every number comes from a deterministic engine. Models only write language over a small aggregate summary. Four tiers: a cloud model, a small open model running inside our own server, the same model on the user's GPU in the browser, and the engine. Small models are guarded: schema-constrained decoding, every rupee figure must exist in the input, and instruction echoes are rejected. The demo cannot break.

The partner pipeline

Messy UPI in. Clean people out.

01
Validate

Types, ranges, codes like invalid_vpa

02
Normalise

"₹1,249.50", +91, PAYTM* prefixes

03
Identify

By phone — UPI IDs change, phones don't

04
De-dupe

By your id and UPI RRN; status updates

05
Filter

Credits, self-transfers, ₹1 penny drops

06
Categorise

Catalog → MCC → keywords → P2P, with confidence

# one payment, as it settlesPOST /v1/events{ "phone": "+91 98765 00009", "amount": "₹349", "payee_vpa": "swiggy.payu@hdfcbank", "payee_name": "PAYTM*SWIGGY LIMITED 4412093" }
202 Accepted"merchant": "Swiggy","category": "food","subcategory": "food_delivery","confidence": 0.97
The pipeline is deterministic — no AI. Validate, normalise, identify the user by phone, de-duplicate, drop junk like self-transfers and penny drops, then categorise using a merchant catalog, about sixty MCC codes, keywords and person-to-person heuristics, each with a confidence score. Webhooks for single payments; batches of up to a thousand, idempotent.

Security model

Built like it handles money.
Because it does.

Keys

Scoped & hashed

stk_live_…, stored as SHA-256, six scopes, shown once.

Tenancy

Strict isolation

Partners see only their own users; other phones are a 404.

Batches

Idempotent

≤1,000 per batch, atomic, safe to replay with an Idempotency-Key.

Traffic

Rate-limited

Per key, with an X-Request-Id on every response.

Consent

Per partner

Anyone can withdraw; only the person or onboarding partner grants.

Sessions

Separated

Portal and app use different token audiences. Demo shortcuts are off in production.

Security is designed in: scoped, hashed keys shown once; strict tenant isolation; idempotent atomic batches; per-key rate limits with request IDs; consent per partner; and separate session audiences for the portal and the app.

How it's built

Production-shaped, laptop-sized.

Client

React 19 · Vite 8 · Tailwind 4 · Motion · Recharts · three.js · WebLLM in a Web Worker

Server

Node 24 · Express 5 · built-in SQLite · JWT · Helmet · rate limits · OpenAPI

AI

Cloud model → Qwen2.5 1.5B via node-llama-cpp (Metal / CUDA / CPU) → on-device → engine

One command: pnpm run setupOne port in productionTested pipeline & guardsMobile-first · dark & light
The stack is modern and boring in the right places: React 19 and Vite on the client, Node 24 with Express 5 and the built-in SQLite on the server. The server model runs in-process through llama.cpp — no Ollama, no external service. One command sets everything up; production is a single port.
